# Fish 模拟开发、问答与数值调优

本 Skill 属于 IGESS 仓库，入口为 `projects/fish_source/README.md`。下文仓库路径均相对 IGESS 根目录；`<source>` 指当前配置解析出的游戏源码根目录，默认是同盘兄弟目录 `E:/fish-oasis`。

## 开始时建立上下文

执行模拟、续跑或分析已有结果前，先按 [IGESS 模拟执行接口](../../../docs/agents/simulation-interfaces.md) 选择平台入口。运行查询、指标定义和目标评估由平台统一提供；本 Skill 负责 Fish 业务口径、策略和调优决策流程。

1. 读取 `projects/fish_source/README.md`、`RoadMap.md` 与根目录 `CONTEXT.md`，区分模拟已接入能力、待办和历史验收结果。
2. 读取 `projects/fish_source/economy.yaml` 的 `engine.source_runtime`，确认实际 `project_root`、`data_root` 与 Lua 入口。相对路径按项目目录解析。旧 `projects/fish` 已停用，旧 Python 模型不作为新规则实现或比较基线。
3. 按问题读取 [代码导航](references/code-map.md) 中相关入口；涉及游戏业务规则时先读 `<source>/simulation/README.md`，再追踪对应服务。涉及另一个仓库的修改时先读取该仓库适用的 `AGENTS.md`，遵守用户范围与实际写权限。

纯问答以当前文件证据回答，不默认启动长模拟或修改代码。迭代开发先明确变化属于玩家策略、宿主接口、游戏规则、数值输入还是报表，沿对应层修改。

付费永久特权模拟先读项目 README 的“开局拥有全部在售永久特权”。`month_1_all_permanent` 按冻结在售目录在第 0 秒经源服务建立权益，沿用免费 `default` 画像与种子派生；核对 manifest 的 `source_profiles.default.permanent_privileges`，区分已购买权益与真实支付、自动操作便利收益。停售永久定义需明确选择，不混入在售组合。权益模式不同不能接续；接口版本改变后重建同版本免费对照，旧报表仍作历史记录。

大 R、付费枪或神兽场景先读 [大 R 场景说明](../../../projects/fish_source/docs/whale-scenario.md)。核对 `initial_loadout`、源 `GunStatsService` 的普通枪参照和青龙的普通鱼参照；初始购买不计新增成长。大 R 独立上阵策略与既有基线不同，比较时同时披露代码身份和策略差异，不能只归因于商品。

## 数值调优协作

固定流程为：**跑报表 → 分析报表 → 给出建议 → 人类决定 → Agent 改表并导出**，再进入下一轮报表验证。报表默认由用户运行，用户明确委托时 Agent 代跑；用户说“看结果”“验证这轮”不意味着重新模拟。Agent 负责分析、建议及决定后的生产改表；人类负责选择调整方案。建议交付后等待人类决定，已有明确选择则直接执行其范围，无需重复确认；用户只要求分析时保持只读。

### 长跑测：提交到已运行的 IGESS，等待人类唤醒

Agent 获准代跑模拟或续跑时，默认通过 [Dashboard 提交脚本](scripts/run_dashboard.py) 调用已运行的 IGESS 实例。本机默认地址为用户选定的 `http://127.0.0.1:8771`，可显式指定其他地址；参数、回执与查询方式见 [服务跑测说明](references/dashboard-runs.md)。任务由服务执行，网页统一显示运行中、成功、失败与报告入口。

1. 完成本轮必要的输入与续跑准备，使用 `submit --scenario <场景>`；续跑传 `--resume-run-id`。沿用服务配置的项目与历史库。服务不可用、项目不存在或所需参数不受支持时报告具体限制，不静默切换到独立 CLI，不自动重启服务。
2. 核对回执 `state=accepted` 后，立即交接场景、Dashboard 链接、任务状态链接和 `submission.json`，说明“IGESS 已接收，跑测是否成功尚待核验；页面显示结束后回复：分析这次跑测”。提交超时为 `submission_unknown`，先查服务与历史，避免重复提交。
3. 长模拟交接后结束当前回合；用户唤醒后再核验并分析。等待期间不轮询、不用 sleep 或 subagent 保持 Agent 活跃。短 smoke 和针对性测试可在当前回合完成；用户明确要求全程跟进时按其要求执行。
4. 用户唤醒后，读取原回执并用 `status` 查询该项目当前任务。核对服务 `instance_id`、场景、动作及历史；`/task` 是项目当前任务，不是永久任务 ID。若服务已重启或期间提交过其他任务，用 `runs list/show/artifacts --json` 按提交时间、场景及输入定位原运行；不能把当前任务或“最新运行”直接视为本轮。成功时通过返回的 `run_id` 核验登记、manifest 和产物；仍运行则交接状态，失败则交付诊断，不自动重复长跑。
5. 默认通知入口是 IGESS 页面与任务状态链接，不承诺 Windows 弹窗或 Agent 在结束回合后主动发聊天消息。关闭网页不取消任务；服务退出可能中断任务。只有用户明确选择独立 CLI、或批准使用服务未支持的 checkpoint 路径／截断参数时，才使用 [旧后台 CLI 说明](references/background-runs.md)。

调用 `fish-balance-loop` 时同样遵守本节：结果验证、打开报告和分析步骤移到人类唤醒之后。

### 目标与不变量

- 每轮读取 `<source>/docs/SettingValue.xlsx`（当前为 `E:/fish-oasis/docs/SettingValue.xlsx`），将其中免费玩家每日养成刺激点规划作为本轮比较起点，而非必然满足的硬约束。Agent 应评估目标本身是否合理；若有更好的成长节奏、目标分布或权重方案，可建议修改该工作簿，说明依据、预期体验收益与取舍，由人类决定后执行。读取当前工作簿，不把历史汇总数或此前建议当作已确认的新目标；目标变更时记录前后值及版本，区分目标调整与生产数值改善。
- 已确认画像为免费玩家每天在线 2 小时。核对实际运行的画像与在线窗口；自然日对应目标列，成长间隔使用累计在线时间。
- 新鱼种、变异鱼种（报表中的新变异组合）的数量受随机收集影响，难以精确控制，作为观察项，不作每日或累计数量的硬性要求。保留实际数量、趋势和既有计数口径；目标表中的对应数量仅供参考，其偏差本身不判定为调优未达标，也不单为凑足这两类数量建议改表。
- “鱼区域”指首次达到新的 FishRandomPool 力量档位，初始池不计；具体去重与边界遵守下文新鱼池成长口径。力量资格与实际入水解锁分别核对。
- 已确认调优不变量为 FishRandomPool 的力量要求、Fish 的基础概率配置与基础 CPS。优先通过其他成长参数和成本接近目标，不自行改变这些不变量。基础概率配置固定不等于不同力量／幸运值下的实际捕获概率相同，基础 CPS 固定也不等于鱼厅总产出固定。
- 幸运值映射、变异配置、玩家策略等额外冻结项，以及目标容差、调优顺序，若仅是 Agent 的建议，应明确标为待确认；不把讨论方案写成用户已接受的约束。

### 每轮分析与交付

1. 定位用户指定的报告与运行目录；按“验证与交付”核对运行状态、产物和身份。优先从现有链接或运行登记获取证据，无法确定是哪轮时询问运行路径或 ID。比较前核对画像、策略、种子、时长、源码／工具版本及所选导表摘要，并确认不变量是否变化；运行输入以冻结快照为准，不用当前生产表冒充当时输入。
2. 对照目标输出“成长项／目标日或数量／实际日或数量／偏差”，将新鱼种与变异鱼种数量标为观察项，按上文口径解读。同步检查关键节点、分类数量、累计进度及在线成长空档；刺激分使用工作簿权重，与去重事件数分开。按目标表选择分类，不直接用报告全部成长事件凑目标总量；新鱼种与新变异的双标签遵守既有计数规则。
3. 沿源规则与运行证据定位瓶颈，区分金币、材料、力量增长、行动时间、系统前置条件、重生恢复和随机收集。检查多项消费是否争用同一钱包，以及收集、图鉴枪和系统开放之间的依赖。目标互相冲突或模拟覆盖不足时明确指出，不靠修改策略、补发资源或改口径制造达标。
4. 给出少量优先调整项，明确是修改生产数值、修改 `SettingValue.xlsx` 的目标规划，还是配套调整两者；包含对应表／字段、建议方向或有依据的候选值、预期改善的节点和可能受影响的其他成长线。区分观察事实、原因推断与建议；证据不足时说明缺少什么，不编造精确改值。每轮优先建议一组可归因调整，交由人类决定采用、修改或暂缓。
5. 人类选定方案后，Agent 按下文“源表修改与委派”修改选定的生产 `.xlsx` 或 `SettingValue.xlsx`；生产表修改还需导出，核对实际改值与决定一致。尚未决定的建议保留为建议；发现需要扩大调整范围时先报告原因，交由人类决定。
6. 收到下一轮报告后，验证已执行的调整是否产生预期效果，并检查连带偏差。固定种子的对照用于观察改动，多种子结果才支持随机差异判断；图鉴枪等依赖随机收集的节点，单次结果不能保证每天精确达标。只有单种子时说明结论范围，需要补跑时给用户明确的运行建议。

一轮分析以交付“主要问题、证据、优先改表建议、下轮验证项”为完成条件。已注册的指标、刺激分和显式目标对照优先使用平台 `metrics/targets` 接口，覆盖不足时说明限制；额外只读计算须注明口径。平台已有结构化目标评估，但不自动导入 `SettingValue.xlsx` 或代表人类认可目标；自动调参和 Fish 多种子扫描不视为已经实现或默认获准执行。

### 源表修改与委派

- 人类决定修改生产数值后，改表执行者读取并使用 `$luban-editor`，按 `<source>` 的适用 `AGENTS.md` 和 Luban 配置定位生产 `.xlsx`、Sheet、字段、注册表与导出命令。修改源项目 `fish-oasis` 的工作簿，再通过项目既有流程生成数据；不要手改导出 JSON／Lua 代替源表修改。
- 人类决定调整目标规划后，Agent 可直接修改 `<source>/docs/SettingValue.xlsx`，使用适用的电子表格技能／工具保留公式、格式与无关内容，重读核对目标、汇总与权重。目标规划表按其实际用途验证，不套用生产 Luban 导出流程；交付修改依据、前后值和后续比较采用的目标版本。仅改目标时可用既有报告重新对照，明确游戏结果未改变。
- 可委派 subagent 使用 `$luban-editor` 执行。交接实际源码／数据根目录、人类选定的方案、允许修改的工作簿／Sheet／字段、改值依据、不变量和验证要求；同一工作簿由一个执行者写入，导出串行执行。主 Agent 复核改表与导出结果后交付。跨仓库写入遵守实际权限，委派不扩大权限。
- 编辑前检查源仓库未提交变更，记录相关单元格／记录 ID、原值与公式；保留无关修改。编辑后重读工作簿，核对新值、公式和 Luban 标记行，再运行项目导出并检查生成数据。确认所选 `engine.source_runtime.data_root` 已包含本轮改动，记录相关导出摘要，并核对调优不变量未改变。
- 改表交付包含工作簿／Sheet／记录／字段的前后值、导出命令与结果、实际数据目录及下轮验证项。导出失败或未更新到所选目录时明确标为未完成，不声称数值已生效；成功导出也不代表成长目标已达成，效果由下一轮报告验证。

## 原项目是什么游戏

Fish 是以摸鱼／炸鱼为主题的增量养成游戏，包含随机收集、经营产出、在线锻炼和重生循环。原游戏在 UE／绿洲启元游戏环境中运行 Lua 服务；IGESS 在无 DS 的数值宿主中复用这些服务。

- 玩家投出摸鱼神器（代码常称 `Torpedo`），力量影响自然飞行落点和水域；鱼与材料结果通过各自随机链结算。
- 鱼进入背包后可上阵摸鱼厅持续产金币，金币先累积在槽位，领取才进入钱包；卖鱼获得一次性资源（材料）。
- 金币投入杠铃，在线锻炼获得力量并影响 Fish Luck；神器影响 Trash Luck。寻宝兽收集并加工废料，完成加工后进入 `material` 钱包，用于资源线养成。
- 力量重生与寻宝兽返祖提供长期成长。读当前源规则确认重置字段、永久收益、突破条件和具体币种，不把阶段性设计描述写死为结算公式。
- 图鉴奖励、图鉴枪、周期鱼潮与鱼蛋孵化形成另一条收集与养成链。真实鱼潮包含射击与争夺；模拟当前采用每场 0 分钟前台占用（开场同秒扣费并入包）、5 颗源随机蛋，并逐蛋按 HP／攻击力向上取整估算发数、以固定 30 发一匣计算源换弹费用的近似（空匣起算，首匣付费，场后余弹不结转）。

设计意图入口：`<source>/gdd/01-核心玩法概述.md`；系统开放查 `54-系统开放规划.md`，枪和鱼潮查 `52-图鉴发枪与鱼潮打蛋.md`。GDD 可能领先实现，例如鱼升级币种、寻宝兽门槛与基础枪补弹规划。回答“目前怎么运行”须追踪当前服务、导表和运行回执；回答“设计想怎样”须注明设计出处。发现两者冲突时说明差异，不自行把规划接入模拟。

## 保持同源边界

- Python 负责玩家意图、行动耗时、上下线、采样、协议与产物；Lua 负责合法性、价格、扣款、奖励、生产和重生。新增行为接入源操作，避免在 Python 复制经济公式或直接改余额。
- Fish 实际数值来自 `engine.source_runtime.data_root`，默认 `<source>/igess_export/json`。本项目 `Datas/` 与 `luban_exports/` 是通用 authoring 结构，改它们不会调整 Fish 数值。生产改表／导出遵守上文人类决定、Agent 执行的流程；测试夹具不得充当生产调优结果。
- 寻宝兽突破成本由 `TrashManRealm.materialRequireToNextRealm` 配置，允许相邻成本下降或持平；源规则只要求非满级成本为合法正数、满级为零，不强制“三小一大”或全局递增。调整节奏仍由人类决定，境界顺序、分解速度和返祖校验独立保留。
- `source_priority_v1` 是模拟玩家策略，不等同于真实玩家或旧 Python 策略。行为权重、操作耗时、在线窗口、自然落点与固定距离对照均须保留可归因身份。
- 神器候选使用源报价 `previousTorpedoId` 检查前置拥有；神器／杠铃按数值 ID 排序，操作与恢复身份仍为字符串。修改候选时同时验证普通选择、鱼潮预留、拒绝冷却及恢复；完整目录／关闭商品契约见项目 README，回归见 `tests/test_fish_growth_candidates*.py`。
- 鱼潮在原绝对周期的开场同秒开始／完成，随后立即继续普通动作，孵化按即时入包时间计；0 分钟是快速打蛋的模拟假设。旧源码／适配器 checkpoint 仍需重建基线。鱼潮采用养成优先、单场余额 25%、30 分钟近期成长预留及当日在线材料收入 15% 累计上限。每日入场必须满足“已付换弹费用加本场完整源报价不超过当日已获得在线材料收入的15%”；日收入包含加工、卖鱼和图鉴材料奖励，排除离线奖励，按模拟自然日重置且不结转。近期成长预测仍排除图鉴奖励。分析材料分配时读取 README 的“养成优先与鱼潮材料预留”，核对 `tide_admission_policy`、三类预算／预留跳过回执及 checkpoint `growth_tide_budget.daily`。修改策略运行 `tests/test_fish_growth_priority.py`、`tests/test_fish_tide_daily_budget.py`、`tests/test_fish_tide_ammunition.py` 及鱼潮／恢复回归；策略改变后重建基线，不复用旧适配器 checkpoint。
- 所有画像先按游戏源“一键最佳资质”换阵，再卖鱼；规则、神兽优先导致的早期无普通参照、1 秒点击耗时及恢复见项目 README 的“一键最佳资质换阵”。仅升级入选且已上阵的鱼，换阵拒绝冷却期间保护入选背包鱼。修改时运行 `tests/test_fish_source_hall.py`、卖鱼和大 R 回归。

## 验证与交付

逐天调参可选 `day_1_growth`～`day_6_growth`；逐周可选 `week_1_growth`、`week_2_growth`、`week_3_growth`、`month_1_growth`，分别累计到 7／14／21／28 天。默认从新玩家运行。输入不变时，用 `--resume-run-id <成功运行ID>`、`--checkpoint-in`（二者互斥）或 Dashboard 历史起点接续到兼容的更长场景；自定义历史库用 `--runs-root` 指定项目目录。完整相邻周接续每次追加 7 天。身份校验保留，旧适配器／改表／配置变化后的 checkpoint 需重建基线。报告仅覆盖新增区间，源恢复仍有历史重放成本；命令和兼容边界见项目 README，验证用 `tests/test_fish_source_continuation.py`。

查询性能维护：先以当前 `<source>/simulation/README.md` 和源码确认已接入能力，不把历史性能记录视为当前实现。幸运值查询由 `ThrowOutcomeResolver.QueryLuck` 与完整 `Resolve` 共用前置映射；默认安全规则只计算四个所需字段，显式 options、异常目录和数值边界回到完整 Resolve 保留错误。修改时运行源 `tests/throw_luck_query_test.lua`，核对精确 DTO、池边界、返回值隔离、随机链和拒绝行为；以逐次完整 Query、核心产物及恢复历史差分验收，同机无探针串行配对计时。

单次完整查询快照复用由 `<source>/simulation/SnapshotScope.lua` 和 Host 的 ArchiveService 注入提供，只在本次 Query、当前会话和 coroutine 内生效；查询结束或异常后清理，嵌套查询独立。各服务的校验选项不同，仍保留原校验。枪查询会修改 combat 投影，必须保持其独立分支；新增查询接入前检查是否修改输入。修改此边界时运行源 `tests/simulation_snapshot_scope_test.lua`，并验证真实跨进程恢复和逐次完整观察，不能只比较终态。

神兽纯产出缓存由源 `FishProductionPolicy.Multiplier` 与 `FishBeastRateCache` 提供。每个存活规则行只保存最后一项：倍率匹配配置及合法数量，产出乘积匹配完整参照与倍率大数字段；返回独立副本，不保存玩家或存档对象。普通鱼参照选择和动态结算仍走原规则。修改时运行源 `tests/fish_beast_rate_cache_test.lua`，覆盖热缓存后的等级／变异／部署、数量、配置、精确参照变化、返回值污染和非法输入，并以正式核心产物、逐次查询和真实恢复差分验收。大 R 同次决策复用只读报价，跨决策不沿用该 Python 对象。证据入口为 `.scratch/fish-whale-rate-cache-20261104/verification.md`。


状态变化观察与推进性能：修改 `observe`、`query_changes` 或冻结生产计算器时，先读源模拟说明的“状态变化观察与冻结生产计算”。消费者仍接收原时点的完整独立状态；传输基准不进 checkpoint，恢复重新建立，完整查询作为回退和差分参照。生产缓存仅用于会话拥有的冻结规则计算器，结算仍使用原精度、校验和回执。验收同时比较逐次逻辑观察与完整业务产物；正式测速关闭诊断记录。
