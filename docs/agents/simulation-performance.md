# 数值模拟性能指南

适用：在 IGESS 新写数值模拟、修改热循环／观察／缓存／调度，以及评估性能。目标是从设计阶段减少重复工作，同时保留规则、可观察行为和恢复契约。

本指南将 2026-10-28～29 Fish 实践提炼为开发与验收要求。文中的性能数字是对应冻结版本的历史证据，不是当前工作区测速，也不是其他模型的性能保证。通用设计建议需要在目标模型中验证。

## 按任务使用

1. **开始写模拟前**：定义工作量与语义，完成“开始前”清单；新模型没有性能基线时，先建立可运行的代表场景。
2. **编写热循环时**：按下文核对状态所有权、重复计算、缓存和事件边界。每项优化写清“省掉什么工作、依赖什么不变量、如何证明结果相同”。
3. **优化已有模拟时**：先冻结基线，再诊断热点；每个候选独立验证语义与收益，最后测组合，避免把多项变化混为一个原因。
4. **交付时**：完成验收清单，给出输入身份、原始耗时、等价证据与限制。只修改文档时检查内容和链接即可，不因此启动性能跑批。

### Fish 的当前范围

新工作使用 `projects/fish_source`，按 [fish_sim](../../.agents/skills/fish_sim/SKILL.md) 建立上下文；模块与测试入口见其[代码导航](../../.agents/skills/fish_sim/references/code-map.md)。原项目 Lua 是规则权威，Python 负责编排、策略意图、观察与报告。

2026-10-29 用户决定停止本轮性能优化，继续尽量直接使用原项目代码；后续默认不继续优化原项目 Lua，也不继续追逐“一周模拟到 60 秒”。只有新的明确任务改变范围时才重新评估。此前已交付优化继续保留。本文提供设计与验收方法，不授权语言迁移、事务框架重写或执行工具包发布。

## 先定义工作量，再讨论快慢

模拟时长相同不代表工作量相同。至少固定场景、玩家策略、动作耗时、种子与随机算法、导表、在线窗口、采样／报告口径和推进模式；同时记录源码、适配器、运行时与输入摘要。优化前后的预期代码差异单独列出。

为代表场景记录启动、输入冻结、源执行／交互、checkpoint、产物和报告成本；正式总耗时以同一入口从开始到全部产物完成的壁钟时间衡量。新脚本先估算：

```text
总成本 ≈ 启动与收尾 + Σ（操作次数 × 每次成本）
观察成本 ≈ 观察次数 ×（快照 + 校验 + 投影 + 编码 + 传输 + 重建）
```

这只是成本模型，各阶段必须互斥才能相加。长程模拟还要考察背包、历史和事件数量增长后每次操作的成本；不能用十 tick 或空背包速度直接外推整周。

预算区分单次运行延迟和多次独立运行吞吐量。并行多种子可以增加单位时间完成的运行数，但不等于缩短一条顺序模拟；性能配对期间并行跑其他模拟反而会干扰结论。

## 热循环：先减少重复工作

### 状态所有权、观察与事务

明确权威状态由谁持有、哪些操作可写、观察结果由谁拥有、失败如何回滚。检查每步是否多次复制整个存档、校验同一快照、扫描／排序同一背包，以及为多个观察者重复构造相同投影。

在同一只读观察范围内，可以考虑共享一次独立快照和一次完整校验，让多个内部投影复用它。前提是投影不修改共享输入，公开返回对象仍隔离，非法状态保持原拒绝行为。写事务继续履行原校验和回滚契约。不能因为“上次校验过”就跳过下一次发生变化后的校验。

前后两次观察必须是独立的逻辑状态：更新后一帧不能污染上一帧，调用方修改返回值不能污染权威状态、缓存或其他会话。否则收入差分、首次成长和回放可能悄悄出错。

跨语言调用应按真实热点减少重复观察、投影和编码。先追踪调用内部，返回小包不一定代表计算少：

```text
# 只减少了传输：完整构造的成本仍然存在
full = build_full_snapshot(state)
send(diff(previous, full))

# 若已证明依赖完备，可复用未变化部分的内部投影
parts = rebuild_changed_parts(state, dependency_versions)
send(explicit_baseline_or_delta(parts))
consumer_state = reconstruct_independent_state(parts)
```

第二种也需测量依赖跟踪、差分和重建成本。增量协议须明确会话／基准身份、删除、空集合、数组顺序和空值；基准不匹配时在同一业务状态获取完整快照或报错，不能重放写命令修复观察。完整查询保留为回退与差分参照。派生传输基准不进 checkpoint，恢复后重建。

### 缓存：依赖、生命周期、所有权一起设计

优先复用输入相同的纯计算。引入任何缓存前，写出这四项：

| 项目 | 需要明确的内容 |
| --- | --- |
| 依赖 | 计算实际读取的全部输入、规则／导表身份及查询选项 |
| 失效 | 哪些写操作或时间变化使依赖改变；如何检测内容变动 |
| 生命周期 | 单次观察、会话或冻结规则实例；容量限制与释放时点 |
| 所有权 | 存入和返回的对象是否可变，调用方修改后是否影响其他结果 |

仅用对象地址或集合长度无法识别原位修改；仅用全局 revision 可能频繁失效，也未必覆盖时间驱动变化。身份值保留完整精度，不用丢失有效位的浮点字符串作为键。

```text
session_cache = bounded_cache()  # 会话关闭释放，恢复重新建立
key = exact_key(frozen_rules_id, all_inputs_read_by_calculation)
if key not in session_cache:
    session_cache[key] = pure_calculation(inputs)
rate = independent_value(session_cache[key])
settle_with_original_rules(rate, current_state, elapsed_time)
```

这段伪代码复用纯产出率，实际结算仍由原规则执行。动态余额、待领金额、交易回执、资格或随机结果不能直接套用它。鱼厅升级、鱼等级／变异／部署、神兽参考鱼、重生倍率等变化必须触发正确结果；命中率不足时，建键和隔离成本可能高于重算。

大数计算、格式转换和序列化也按热点证据处理。精度、舍入顺序、拒绝语义及 DTO 契约属于结果的一部分；不能以浮点近似换取表面加速。

### 调度与批处理：保留真实事件边界

只有已证明区间内不会改变决策与结算语义时，才合并推进。列出定时任务、buff、动作完成、飞行、孵化、上下线、采样与玩家决策边界；保持边界上的事件顺序、随机数消耗顺序、回执和 revision。

验证至少包含边界前／恰好边界／边界后、同刻多个事件，以及原接口允许的非整数时间。满背包阻塞后恢复容量、待完成保存／通知、截断后续跑都可能使“空区间”假设失效。

保留准确路径作对照。事件队列维护或额外状态检查可能抵消批量收益；应先做最小实验，语义相同但未证明更快的候选不默认接入。

## 测量：将热点归因与正式成绩分开

- **正式成绩**：使用实际正式入口、最终拟交付源码字节和相同输入；关闭性能探针与逐次诊断日志。同机串行执行，记录硬件／运行时、后台负载、运行顺序和每次耗时。已有模拟默认至少三组目标场景配对，报告中位数、范围和每组差值；兼顾短场景是否回退。若有明显顺序漂移，补充交错顺序配对。
- **热点诊断**：临时探针用于解释成本与调用次数。inclusive 计时存在嵌套，不能相加；VM 指令采样比例不是 CPU 时间比例；Python CPU 时间不含其等待 Lua 的整段壁钟时间。带探针耗时不能充当正式收益。
- **实际加载版本**：核对运行清单的源码／适配器／导表身份，确保运行进程加载了候选。Dashboard 每任务新进程及服务自身重启边界见[任务进程说明](../dashboard-task-processes.md)。保存文件不等于所有已启动服务都完成更新。
- **比较分母**：每轮使用自己的冻结基线，不能把上一轮更慢版本继续当作本轮分母。不同候选的单项收益不直接相加；不同阶段的中位数也不要求相加等于总耗时中位数。

可以用 `预计新耗时 ≈ T × ((1 - p) + p / s)` 筛选候选，其中 `p` 必须是可比工作量中不重叠的目标成本占比，`s` 是该部分假设加速倍数。这个估计假设其余成本不变；含探针／等待重叠的粗略占比只能作规划参考。更换宿主语言与改变进程／数据交换结构应分开实验，最终收益仍由正式配对证明。

## 验收：相同终值不足以证明等价

按改动影响选用现有回归与差分工具，检查业务输出而不是私有缓存键或调用次数。性能测速与普通正确性测试分开；避免把容易抖动的毫秒阈值加入普通单元测试。

| 改动涉及 | 必须关注的等价证据 |
| --- | --- |
| 状态观察、变化传输 | 原观察时点逐次完整逻辑状态和查询选项、返回对象隔离、非法输入拒绝码、基准错配与完整回退 |
| 缓存、纯计算复用 | 每类实际依赖变化、动态字段变化、多会话、返回值被修改、缓存冷启动及恢复重建 |
| 时间推进、调度 | 行为决策／事件顺序、随机结果、精确金额、完整终态、源操作／回执历史、边界与待完成副作用 |
| checkpoint、恢复 | 连续与真实跨进程恢复一致，操作身份不变，重复请求不重复扣款／发奖，原代码身份限制仍有效 |
| 正式运行与报告 | timeline、events、成长／行为核心产物字节，checkpoint 行为字段和完整 Query DTO；按影响核对报告业务字段 |

只对白名单内的代码身份、路径和耗时等非业务字段做比较归一化，写清理由；不能排序事件掩盖顺序差异，或忽略整个业务对象。给比较器至少一个篡改业务字段的负例，确认它确实会拒绝错误结果。

保留既有失败和环境跳过的证据。定向测试通过不等于全套通过；跨版本 checkpoint 拒绝不等于应放宽身份校验。正式产物成功也不代表 UE、DS 或执行工具包已验收。

## 开发与交付清单

### 开始前

- [ ] 工作量、性能目标与允许修改范围明确，区分单次延迟和多次吞吐量。
- [ ] 场景、策略、随机、输入、采样与报告口径确定；已有模拟冻结实际基线，新模型建立代表场景。
- [ ] 权威状态、观察所有权、事务、随机链与 checkpoint 边界明确。
- [ ] 预计调用次数和随库存／历史增长的成本已检查，测量入口及计时范围明确。

### 编写热循环时

- [ ] 每项优化能说明省掉的重复工作；增量传输与内部计算成本分别检查。
- [ ] 缓存列出完整依赖、失效条件、生命周期／容量及返回对象隔离方式。
- [ ] 批处理保持事件、决策、观察和随机边界；精度、拒绝、回滚与幂等语义保留。
- [ ] 诊断可关闭，准确／完整路径可用于差分；没有通过削减业务工作量制造加速。

### 验收时

- [ ] 使用实际拟交付字节与输入身份，正式入口多组串行配对，保留原始值、顺序、中位数与范围。
- [ ] 按影响完成逐次观察、核心产物、终态、checkpoint／恢复及比较器负例检查。
- [ ] 明确已通过、未覆盖、既有失败与环境跳过；有证据才声称性能收益。
- [ ] 收益无法超出噪声、依赖无法证明完备、或需越过用户范围时停止该候选，记录结论。

交付说明至少包含：优化假设与实际变化、基线／候选身份、测量条件与原始耗时、等价验证路径、未覆盖项、采用或停止的理由。复用已有本地 issue／验收记录即可；经验影响本指南时更新对应段落，具体代码入口由项目技能维护。
